# README Structure Playbook

Read this reference when designing the README structure, preview, incremental change, or visual evidence.

## Dynamic Structure

Select modules from the project type, reader questions, primary action, and available evidence. Do not force badges, screenshots, installation, architecture, roadmap, contribution, or any other section into every repository.

The opening normally needs a literal project name, a reader-centered value statement, one clear next action, and concrete product evidence when the repository is visual. Treat these as defaults, not decoration rules.

## Representative Preview

Before editing, show enough real proposed content for the user to judge the result:

1. project type, audience, visibility, language, and strongest evidence;
2. proposed information architecture;
3. first-screen title, value statement, and introduction;
4. stable `P1 Preserve`, `R1 Rewrite`, `A1 Add`, or `D1 Remove` items;
5. section-level before and proposed text for changed sections;
6. evidence gaps and assets requiring confirmation;
7. proposed GitHub metadata, clearly separated from README edits.

Do not substitute a thumbnail collage, compressed whole page, section-name list, wireframe, or generic style board for representative text and content hierarchy.

## Incremental Mode And Scope Lock

Convert approved item IDs into an explicit scope lock. Approval of one item does not approve adjacent sections or the full proposal.

For a section-only request:

- inspect surrounding content for contradictions;
- edit only the named section and directly necessary repairs inside it;
- list every unapproved section under `Outside scope`;
- turn contradictions elsewhere into separate proposal IDs;
- apply the smallest coherent edit after approval.

The user may accept, revise, defer, or reject each item. Preserve those decisions throughout later iterations. If user feedback conflicts with a proposal, update the preview and request approval for the revised item; do not treat discussion as edit authorization.

## Visual Evidence

- Use real screenshots, demonstrations, or video for visual products when available.
- Use real terminal output, working examples, request/response samples, or diagrams for CLI, libraries, and APIs.
- Use natural-language invocation examples, output artifacts, and evaluation evidence for Agent Skills.
- Label prototypes, simulations, historical captures, and unverified visuals.
- Never fabricate a product screenshot or use unrelated art to imply product completeness.
- Creating, changing, generating, or uploading an asset requires separate approval.

When rendered visuals matter, inspect the actual result through an available browser path. Wait for intentional entrance motion to settle before taking a static screenshot, while also checking that the initial loading state remains readable.
